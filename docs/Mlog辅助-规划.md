# Mlog辅助 · 路线图与详细方案（P2–P5）

日期：2026-10-29 · 上游文档：`docs/Mlog辅助-设计.md`（P1 契约，已实现，commit c25d1c7）

## 0. 目标形态（用户 m08103 原话）

> 我想的是用热键框选一个区域，然后描述要写什么逻辑，排入队列由大模型处理。完成之后写入。

一句话：**玩家不写 mlog，也不在面板里挑模板** —— 框一片地，说一句要什么，剩下的交给流水线。

```
F7 框选矩形
   -> 区域快照 JSON（处理器 / 可连方块 / 现有代码 / 单位 / 资源）
   -> 玩家一句话描述 + mode(new|edit)
   -> 入队（落盘 queue/<jobid>.json + POST /jobs）
        sidecar worker（串行，可取消）
          -> prompt = 快照摘要 + 描述 + 规则摘要
          -> provider（可插拔 LLM）-> 结构化候选 {code | template+params, explanation, assumptions, needs_links}
          -> 门禁：mlogcheck 全量 41 条 -> cost（ipt 40 / 1000 语句）-> 可选 mlogsim 200 tick
          -> ERR 且有重试次数：把 findings 回灌模型重试（最多 2 次）
          -> done / rejected / failed / cancelled
   -> 游戏内提示「N 个处理器就绪」-> 预览 diff -> 确认写入（原版 config 通道）-> undo
```

## 1. 已定的三个分叉（用户 m08110「就按照这个顺序」= 接受建议）

| 问题 | 决定 | 理由 |
|---|---|---|
| 一个区域 = 一个逻辑，还是多处理器分工？ | 先做**每个处理器各一段**；多处理器协同（world processor 下发一片）留到 P5 之后 | 多处理器要解决寻址、共享内存、跨处理器同步，是另一个难度级别；先把单处理器闭环做扎实 |
| 模型走哪家？ | sidecar 里 **provider 可插拔**，默认读环境变量（OpenAI 兼容，DeepSeek 即可），本地模型以后接 | 不把产品绑死在一家服务上；协议层不知道模型是谁 |
| 框选里的现有代码算不算上下文？ | 都带，用 `mode: new | edit` 区分 | `edit` 是「把这段改成……」，`new` 是「从零写」；同一个快照字段，两种 prompt |

## 2. P2 · 快检进游戏（本轮实现）

### 2.1 为什么需要它

P1 里所有判断都在 sidecar：sidecar 没启动、模型慢、队列排着，模组就是瞎子。
快检让模组**离线也能说人话**：「`turret1` 这个名字没连到这个处理器」「这条指令要 build 157」。
它同时是 P4 的前置：模型回来的代码，游戏里先过一遍快检，再决定要不要显示「就绪」。

### 2.2 边界：快检 ≠ 全量，故意不做的事

| 全量（sidecar，Python） | 快检（模组，JS） |
|---|---|
| 41 条规则，含未赋值变量的**槽位分级**（num/bool 槽 INFO、obj 槽 ERR） | 不做未赋值变量分级（槽位表要跟 mlogcheck 同步，重写即漂移） |
| `cost_report`：CFG 最长路径 + 环路 bound + 死代码 | 只算**线性指令数**（环路按 1 遍），标注「快检估计」 |
| 值域分析、跨处理器、pin 流 | 不做 |
| 链接名是否绑定的完整判据（含链接形变量识别） | 只看「名字在不在 b.links 里，且没被 set 过」 |

**原则：快检只查「单行 + 一张数据表」就能定的事实**。任何需要控制流/数据流推理的东西都不进 JS，
因为那会变成第二份实现，两份实现必然漂移，而漂移的检查器比没有检查器更糟。

### 2.3 数据从哪来（唯一真源仍是 Python）

`tools/rules_export.py` 从现有表导出 `MlogAuxiliary/scripts/rules.generated.js`：

| 导出项 | 来源 | 用途 |
|---|---|---|
| `INSTR`（53 条：arity / defs / uses / min_build） | `tools/instr_semantics.json` | 未知指令、版本门 |
| `OPS`（45 条：min_build） | 同上 `ops` | `op emod`/`op ushr` 的版本门 |
| `SUBCMD`（ucontrol 20 / draw 16 / ulocate 4） | 同上 `subcommands` | 子命令拼错（编译成 noop） |
| `LINK_SLOTS`（9 条） | `tools/mlogcheck.py:462 LINK_SLOTS` | 链接名槽位 |
| `BASELINE_BUILD = 146`、`IPT_MAX = 40`、`MAX_INSTR = 1000` | `mlogcheck.py:474`、`LogicBlock.java:46,48,826` | 版本基线、成本门 |

生成物头部写 `// GENERATED by tools/rules_export.py -- do not edit` + 内容 sha256 + 行数。

### 2.4 快检算法（`MlogAuxiliary/scripts/quickcheck.js`，纯函数、无游戏依赖）

```js
MAI_QUICKCHECK.check(rules, code, linkNames, {build: 160})
// -> {findings: [{sev, line, rid, msg}], stats: {statements, linearCost, floor, truncates}}
```

五条判据（每条都只读单行 + 数据表）：

1. **未知指令**：首 token 不在 `INSTR` 且不是 `op` 的子命令 → WARN（模组指令或拼错）。
2. **子命令拼错**：`ucontrol/draw/ulocate` 第 1 槽不在 `SUBCMD` → WARN（`LParser` 会把它编成 NoopI，静默不执行）。
3. **版本门**：语句所需 `min_build` > 当前 build → WARN（在旧版本上被替换成 noop）。
4. **链接名未绑定**：链接槽位里的裸标识符不在 `linkNames` 且从未被 `set` → WARN（`LExecutor` 取 null，指令静默无效）。
5. **体积**：语句数 > 1000 → ERR（导入时尾部被静默截断）；线性指令数 / ipt 报「跑完一轮要几个 tick」。

行号一律是**代码行号（1 起）**，与 sidecar 的 `line` 同义；标签行与注释不占语句但占行号。

### 2.5 验收

- `python tests/mlogauxiliary/run_quickcheck_tests.py`（不需要 JRE，实测 0.3 s）：
  ①`rules_export.py --check`：磁盘上的 `rules.generated.js` 与重生成结果逐字节相同（漂移即 FAIL）；
  ②`require()` 契约：`rules.generated.js` / `quickcheck.js` 能被 CommonJS 加载（游戏就是这么加载的）；
  ③**14 个**快检用例（好代码 0 findings、未知指令、拼错子命令、版本门两个 build、断链名、已声明变量不误报、1001 条截断 ERR、标签不算语句…）；
  ④**单向交叉验证**：快检报 `link-name-not-bound` 的行，`mlogcheck.analyse()` 必须也报同一行——少报允许，瞎报不允许。
- `gate.py` 新增 `quickcheck` 步（默认档，无 JRE，实测 0.3 s）。
- 游戏内：F4 面板选处理器即显示「本地快检」三行；`maiScan()` 扫全图处理器并打印耗时（目标 100 处理器 < 1 s）。
  **这一条没有机器验证**：无头模拟器里没有界面，面板与热键只能靠人上手看。

### 3.2 快照 schema（`snapshot v1`）

| 字段 | 内容 | 备注 |
|---|---|---|
| `v` / `t` | 快照版本、时间戳 | |
| `bounds` | `{x1,y1,x2,y2}` tile 坐标、`w/h` | |
| `map` | 地图名、尺寸 | |

| `candidates[]` | 每个处理器 10 格内**可连**的方块 `{name, block, x, y, dist}` | 链接名白名单（`findLinkName` 规则：末段+序号） |

## 4. P4 · 队列 + 模型 + 门禁

### 4.1 job 契约

```json
{
  "id": "<sha1(snapshot+desc+mode)[:16]>",
  "created": 1792..., "state": "queued|running|done|rejected|failed|cancelled",
  "mode": "new|edit", "desc": "给这片区域做补给，每 5 秒检查一次核心物品",
  "snapshot": { ... }, "attempts": 0, "findings": [], "code": "", "explanation": "", "assumptions": [],
  "reasoning": "<最近一次尝试里模型的 reasoning_content，v0.12.4>"
}
```

落盘 `<dataDir>/mlogauxiliary/queue/<id>.json`（模组写）+ `POST /jobs`（sidecar 收），双写保证 sidecar 崩了不丢。
状态推进由 sidecar 负责，模组轮询 `GET /jobs`（1 s 间隔，面板关着也轮询，完成后弹提示）。

**模型思考过程（v0.12.4）**：推理模型先写 `reasoning_content` 再写 `content`，玩家点「生成」后如果只看到
`被门禁拒绝（ERR 1 条）` 加一行 message，是分不清「模型想歪了」还是「没照做」的。所以 sidecar 把回复里的
推理内容摘成 `reasoning` 存进 job（`tools/mlogprovider.py` 的 `_reason_text()` / `_with_reason()`，
上限 `REASONING_MAX = 12000`；`tools/jobqueue.py` 的 `_run()` 在 provider 返回后写入，上限 20000），
模组 `renderJob()` 在状态行下面摊开开头 16 行 × 40 字符。端点不返回推理内容时这段不出现。

### 4.2 端点（在 P1 四端点之上加三个）

| 端点 | 语义 |
|---|---|
| `POST /jobs` | 入队（body = job），返回 `{ok, id, state}`；**还在飞**（queued/running）时 `id` 冲突视为幂等，已终态（done/rejected/failed/cancelled）后同 body 起新跑 |
| `GET /jobs?id=` / `GET /jobs?state=` | 查一个 / 列未完成的 |
| `DELETE /jobs?id=` | 取消（running 也取消，worker 在下一个检查点退出） |

**历史与在飞是两个问题（v0.12.5）**：`GET /jobs` 不带参数只答在飞（queued/running），作业管理窗要的是发生过什么，所以加 `all=1`（`limit` 默认 50、夹在 1..200）：此时返回全部作业按 `(created, id)` 降序，并用 `job_brief()` 剥掉 `snapshot`/`code`/`bytes_b64`/`reasoning`/`links`/`assumptions`（列表每秒拉一次，不能几十 KB 地拖）。要看完整的还是按 id 单取。

**幂等只对「在飞」成立（v0.12.2）**：job id 是 `sha1(snapshot+desc+mode)[:16]`，也就是内容寻址。
最初把「同 body 二次提交」一律当幂等回旧作业，结果是**已终态的作业把自己的内容 id 粘住了**——
一条死在 `provider-error: empty reply` 的作业，玩家把端点修好后原地再点一次「生成」，拿回来的还是
那条 `empty reply`，模型根本没有被再问一次。现在终态作业不再占着内容 id：同一个 body 会起
`<id>-2`、`<id>-3`…（带 `retry_of` 指回首轮），失败的那次仍留在盘上可对比。模组不用改，也不用重装。

### 4.3 两档生成（先锚定，后自由）

| 档 | 模型输出 | 门禁 | 风险 |
|---|---|---|---|
| **锚定**（先做） | `{template, params, explanation}`，从六个（后续十个）模板里选一个 + 填参数 | 参数类型校验 + 模板生成的代码过全量 check | 表达力有限，但几乎不可能出语法错 |
| **自由**（后做） | `{code, explanation, assumptions[], needs_links[]}` 整段 mlog | 全量 check + cost + 可选 sim 200 tick | 幻觉链接名/版本漂移/死循环，全靠门禁与 self-repair 兜 |

self-repair：门禁返回 ERR 时，把 `findings`（行号 + rid + msg）作为下一轮消息追加，最多 2 次；
仍失败 → `rejected`，把 findings 给玩家看，**绝不写入**。

### 4.4 prompt 结构（三段）

1. **世界事实**：快照摘要（处理器清单、可连方块、单位/资源计数），明确告诉模型「链接名只能从这张表里取」。
2. **规则摘要**：指令表（名称 + 参数个数）、版本门、ipt 上限、1000 语句上限、`name:` 标签语法。
3. **任务**：玩家原话 + `mode` + 输出契约（JSON schema）+ 「不确定就写进 assumptions」。

### 4.5 验收

- 离线造 job（不接模型，用假 provider）跑通状态机：queued → running → done/rejected/cancelled，双写落盘可续。
- 假 provider 故意返回坏代码（幻觉链接名）→ 必须 `rejected` 且 findings 带 `link-name-not-bound`。
- 真 provider 跑 5 个真实描述，成功率与 self-repair 次数记进报告（不写死期望值）。

**实际落地（P4 第一刀，2026-10-30）**：队列、状态机、门禁先做出来，**不接模型** —— {BT}tools/jobqueue.py{BT}
（{BT}normalize/job_id/gate/Store/Queue/template_provider/FakeProvider{BT}）+ {BT}logicd{BT} 三个端点
（{BT}POST /jobs{BT}、{BT}GET /jobs?id=|?state={BT}、{BT}DELETE /jobs?id={BT}）。已落地：§4.1 的 job 契约与状态机、
每次跃迁 tmp+{BT}os.replace{BT} 落盘、重启时 {BT}running -> queued{BT}（attempts 保留）、POST 幂等、
running 也能取消（worker 检查点退出）、最多 3 次尝试（1 + 2 次 self-repair）。
**门禁比分析器严一档**：{BT}link-name-not-bound{BT} 在 {BT}mlogcheck{BT} 里是 WARN（人还没接完线是常态），
但机器写入必须拦，所以 {BT}FATAL_RIDS{BT} 把它提升为 ERR；{BT}rejected{BT} 的作业 {BT}code{BT} 恒为空串。
provider 是唯一接模型的缝：默认 {BT}template_provider{BT}（复用 §3 之前的意图路由，离线可跑），
测试用 {BT}--jobs-provider fake{BT}。**未落地**：模组侧 1 s 轮询 {BT}GET /jobs{BT} 与完成提示（游戏内 UI 下一刀）、
真 provider、prompt 三段（§4.4 的组装要等真 provider）、§4.3 自由档的 sim 200 tick 复检。

**实际落地（P4 第二刀，2026-10-30）**：游戏侧接上了队列 —— F4 面板不再直接 `POST /plan`，
而是 `POST /jobs` 投作业 + 每秒 `GET /jobs?id=` 轮询（`JOB_POLL_MS = 1000`），
done 时渲染代码并把按钮换成「写入/关闭」，rejected/failed/cancelled 时渲染 findings 与原因，
面板上多一个「取消作业」（`DELETE /jobs?id=`）。「直接生成」保留给没有 `/jobs` 的旧 sidecar。
**仍未落地**：§4.3 自由档的 cost/sim 复检、P5 的多处理器事务写入。
**盲区已修（v0.9.0）**：处理器**一个链接都没有**时模组发来的 `links` 是空数组，而 `mlogcheck` 原来把空数组
当「不知道」而不是「确实没有」，幻觉链接名在这种情况下拦不住。现在 `mlogcheck.analyse()` 有 `links_authoritative`
开关（默认 False，行为不变），`logicd.analyse()` 在 `links is not None` 时置 True，`jobqueue` 把 `null`（不知道）
与 `[]`（确实没有）分开保留。零链接处理器上的 `sensor x container9 @copper` 现在必 `rejected`（L2-44）。

**实际落地（P4 第三刀，2026-10-30）**：`tools/mlogprovider.py` 把 §4.4 的三段 prompt 与 §4.3 的回复契约做成可离线验的代码 ——
`build_prompt(job, hint)`（世界事实 = 处理器坐标 + 快照摘要 + 附近方块统计 + 链接名白名单；`links is None` 写「UNKNOWN」，
`links == []` 写「EMPTY」；规则摘要；任务 + JSON 契约，self-repair 时把上一轮 findings 逐条附上）、
`parse_reply(text)`（只取第一个配平的 `{...}`，容忍围栏与散文，字段类型不对抛 `ProviderError`）、
`HttpProvider`（OpenAI 兼容 `/chat/completions`，标准库 urllib，key 只从环境变量读，导入时不联网）、
`ScriptedProvider` / `load_script`（回放录制回复，测试与回归全离线）、`Recorder`（`--llm-record` 追加 `{prompt, reply}` JSONL）。
CLI：`--jobs-provider llm` + `--llm-url/--llm-model/--llm-key-env/--llm-timeout/--llm-max-tokens` 或 `--llm-replay`；两者都没有就 `exit 2`（不静默回落模板档）。
`needs_links` 里出现白名单外的名字由 `jobqueue` 直接判 `link-name-not-bound` ERR 拒绝，不等分析器发现。
验收：`tests/logicd/run_logicd_tests.py` 的 half D 共 **9 项**（三段 prompt、白名单三态、围栏/散文解析、垃圾回复拒绝、
scripted 干净回复 → done、幻觉链接 → rejected、self-repair 第二轮 prompt 带 findings、`needs_links` 越界拒绝、
CLI 无端点 exit 2、replay 文件回放、CLI `--jobs-drain` 用 replay 跑完一台作业）。
**仍未落地**：真端点从未在本机联调（无网络/无 key，CI 里只走 replay）、自由档的 cost/sim 200 tick 复检、
模组侧选择 provider 的界面（目前只能改 sidecar 命令行）、P5 的多处理器事务写入。

**回复预算（v0.12.3，真机回归驱动）**：现在的模型档多半是推理模型（先写 `reasoning_content`、再写 `content`），
两者**共用** `max_tokens`。预算偏小时回复不是「短」，而是**空的**：真机作业 `f122e54f918974ff-2` 的 finding 是
`model endpoint answered with an empty message (finish_reason=length; message keys=content,reasoning_content,role;
usage={"completion_tokens": 1600, "prompt_tokens": 502})` —— prompt 只有 502 token，1600 全花在思考上。
所以 `DEFAULT_MAX_TOKENS` 提到 4096（上限不是目标，模型写完就停）、`HttpProvider` 见到
`finish_reason=length` 自动升一档重试一次（×4，封顶 16000，超时同档放宽），仍不够就把
`--llm-max-tokens` 写进错误里；预算可在设置页/端点里改（`POST /llm {max_tokens}`、`GET /llm` 回报、
CLI `--llm-max-tokens`）、`POST /llm/probe` 的预算也从 128 提到 512 起（128 对推理模型连一个 JSON 都写不完，
自测会假阴性）。`GET /health` 同时开始回报 `version`，一眼看出跑的是不是新进程（L2-51 / L2-52）。

## 5. P5 · 多处理器写入 + 撤销落盘

- 一个 job 可产出 N 段代码（每处理器一段），写入是**事务**：全部预检通过才逐台写，任一台失败回滚已写的。
- 写前快照落盘 `<dataDir>/mlogauxiliary/undo/<jobid>/<x>_<y>.json`（原 code + links + 时间），撤销逐字节还原。
- 联机：写入走 `build.configure`（服务端执行），客户端只负责排队与提示；权限不足时明确报「无权限」。
- 冲突：写入前重读处理器 code，与快照不一致 → 提示「处理器在你提交后被改过」，让你选覆盖或放弃。

### 第一刀（v0.10.0，已落地）：撤销落盘

只做上面第二条里与「撤销」有关的部分，而且**故意做得比规划更小**：

- 目录是平的 `<dataDir>/mlogauxiliary/undo/<毫秒时间戳>_<x>_<y>.json`，不是 `<jobid>/` 子目录 ——
  一个作业当前只写一台处理器（事务写入还没做），按作业分目录等于每个目录一个文件，反而更难找「最新一份」。
  时间戳前缀让文件名排序 = 时间顺序，撤销永远取最新那份。
- 每份快照存 `{schema, x, y, at, why, code, links[]}`（`why` 是 `write:<模板id>`，将来作业档会是 `job:<id>`）。
- 只还原代码：模板生成的链接表来自处理器**当前**的链接，回滚 `b.code` 就够了（`updateCode`）；
  链接表一并存下来是为了第二刀（事务写入时按快照逐字节还原）与人工排查。
- 上限 40 份，写新的就删最旧的；处理器已被拆掉（`Vars.world.build(x,y)` 不是处理器）的快照跳过并继续往前。
- 内存栈仍然优先（关游戏前撤销最快，也不需要落盘）；磁盘只是「关游戏之后」的兜底。

**还没做**：一个作业产出多段代码时的事务写入与整体回滚（要扩 sidecar 的作业契约）；写前冲突提示已在第二刀落地（见下）。
### 第二刀（v0.10.1，已落地）：写前冲突检测

规划里「写入前重读处理器 code，与快照不一致 → 提示被改过」这一条先做了**模组侧的一半**，
因为真正的多处理器事务还要等 sidecar 作业契约扩展：

- 基线不是「撤销快照」，而是**投递那一刻的代码**（`JOB_ORIG`）。撤销快照是写入前一刻才拍的，
  拍完立刻写，中间没有给人改代码的机会；作业却是异步的，等待窗口才是冲突窗口。
- 不做对话框，改成「拒绝一次 + 再点一次算确认」（`JOB_FORCE` 只放行一次）。原因：无头环境
  `Core.scene` 为 null，弹窗 NPE，而这条路径在真机与测试里是同一条。
- 写入成功后基线过期（`forgetOrig`），避免下一次写入误报。
- 两条投递路径都要记基线：`jobSubmit()` 与 `jobSync()`（后者是控制台/测试入口，最初漏记，
  端到端用例直接暴露：第一次写入没有拒绝）。


### 第三刀上半（v0.12.0，已落地）：事务写入核心

规划里「一个作业产出 N 段代码」这一条改成**模组侧用 N 个作业协调**，不扩 sidecar 的作业契约：

- 每台处理器各投一个作业，链接表 / 门禁 / 修复循环天然按台独立（比一个作业塞 N 段代码更准）。
- 写入是事务：整批预检 → 整批冲突检查 → 整批落盘快照（同一个 `batch`）→ 逐台 `configure`；
  任一台抛错就把已写的按快照 `updateCode` 回滚。
- 撤销按批次：快照 JSON 加 `batch` 字段，`undoBatchFromDisk()` 整批还原。
- **还没做**：面板上的「批量投递 + 同时轮询 N 个作业」（下一刀）——**已完成（v0.12.5）**；权限不足的联机提示——**已完成（v0.12.8）**：队伍不对当场拒（`permWhy()`，一台都不写），其余情况写完 1.5 s 回读 `b.code`，对不上就 `hint()` 报「无权限：… 的写入没生效（服务端没有接受）」。冲突检测也不再只比代码文本：链接表签名（`JOB_LINKS` / `linkSig()`）一起比（v0.12.8）。

## 6. 风险表

| 风险 | 对策 |
|---|---|
| 模型幻觉链接名 | 快照的 `candidates[]` 是白名单；`link-name-not-bound` 兜底；ERR 不写 |
| 模型写死循环/超成本 | `cost` + 可选 sim 200 tick；超 1000 语句 ERR |
| 快检与全量判据漂移 | 快检只做单行事实；数据表由 `rules_export.py` 生成 + gate 逐字节校验 |
| Rhino 主线程卡死 | HTTP 与模型调用全在 `Threads.daemon` + `Core.app.post` 回主线程 |
| 队列丢活 | 双写（文件 + POST），sidecar 重启扫描 `queue/` 续跑 |
| 写坏存档 | 预检全过才写 + 写前快照 + 一键撤销 |
| 隐私（代码与区域信息发给模型） | 首次使用时明确提示；provider 可换成本地模型 |

## 8. 明确不做

- 不做「自动改你已有的程序」而不给你看 diff。
- 不做无门禁的写入（哪怕模型很自信）。
- 不在 JS 里重写全量规则。
- 不把 sidecar 整体搬进游戏内 Rhino（JS 移植）：成本与风险已单独评估，见
  `docs/Mlog辅助-JS移植评估.md`（估 3,000–3,500 行 JS / 14–20 人日，两份实现长期并存）；v0.13.1 用「随包 exe + 模组拉起」把玩家侧的依赖降到了零，先不做这一步。
- 不做多处理器协同寻址（P5 之后单独设计）。
- 不把玩家存档内容默认上传；只在提交 job 时发送该 job 的快照。
